# M26 — Operator onboarding

## Pre-implementation audit (7 October 2026)

- Baseline: clean `feature/v2-operator-onboarding`, M25/V22. No repository/ancestor AGENTS.md found.
- Users have unique email, required phone/password hash, ACTIVE/INACTIVE/LOCKED and soft deletion. Public registration creates CUSTOMER; BCrypt cost 12 and the shared PasswordPolicy enforce 8 characters / 72 UTF-8 bytes. Invitations must create a dedicated identity through these same primitives.
- Roles use `roles` plus `user_roles`; operator membership is `operator_staff`, with unique operator/user and operator/staff code. Context requires exactly one active membership and explicitly denies SYSTEM_ADMIN. JWT identity reloads user roles; login is independent of operator status.
- OperatorStatus contains ACTIVE/INACTIVE only. Reuse INACTIVE before acceptance; add only SUSPENDED. An application link distinguishes onboarding from legacy inactive operators.
- M13 admin APIs/UI offer directory, detail, direct operator/admin creation, profile update, and unrestricted status patch. M26 must prevent this legacy patch from bypassing invitation or suspension transitions.
- M24A public profiles, discovery and trip search explicitly require ACTIVE; reviews are separate and need no changes. Trip holds, booking creation and payment confirmation lock/revalidate ACTIVE. Assisted sales reuse hold/booking services. Modification requires ACTIVE.
- Existing membership queries reject all non-active operators, inadvertently preventing M25 service for passengers. Permit SUSPENDED membership, while retaining commerce checks and adding supply guards. INACTIVE remains denied.
- Full and partial cancellation currently reject non-active operators. Allow SUSPENDED explicitly while retaining INACTIVE, cutoff, attendance, lifecycle, refund and inventory rules.
- Existing operations/lifecycle services enforce tenant membership and trip locks. Keep those guards and transitions for scheduled, boarding and departed trips; suspension itself never changes passenger records.
- M23 notifications require a booking and persist email deliveries. Add optional booking linkage for accountless application receipts/rejections only. Never send or persist invitation secrets through this outbox. SMTP worker remains asynchronous.
- Auth UI uses normal `/login`, role-based destinations and separate admin/operator guards. Add public application and invitation pages; no customer registration during onboarding.
- Demo seeder is restricted to demo/non-production profiles but resets known demo operators ACTIVE on rerun. Preserve an existing SUSPENDED demo status.
- No public multipart/file-upload service exists; existing public profile image fields are URLs. M26 collects no uploads or legal documents.
- Commercial lock order is trip(s) in ID order → operator → booking/payment/inventory. Suspension locks only operator and must never acquire trip locks afterward. Application decisions lock application; acceptance/reissue lock application → operator → invitation. Unique legal identity slots and token hashes handle duplicate submissions/races. Supply creation must avoid introducing operator → existing-trip/bus inversions.

## Workflow decisions

SUBMITTED → UNDER_REVIEW → APPROVED; SUBMITTED/UNDER_REVIEW → REJECTED. No direct approval. Rejected records remain terminal; new submissions can reuse their normalized legal code. SUBMITTED, UNDER_REVIEW and APPROVED reserve that code through a generated unique key. Approved operators also have a unique legal code.

Approval creates INACTIVE operator and a 72-hour invitation; it creates no user/password/supply. Secure random token is returned once, SHA-256 only is stored. Reissue revokes old invitations. Acceptance serializes with reissue, creates a new BCrypt user, OPERATOR_ADMIN role and active membership, consumes the invitation and activates the same operator. Existing emails always require a dedicated email instead.

Suspension restricts new commerce and supply, preserves existing booking reads and permitted cancellation/refund and trip service. Reactivation requires completed onboarding and a valid single-operator, dedicated active admin. Governance history is append-only through the application; no update/delete endpoint exists.

SYSTEM_ADMIN governs applications/operators only, without impersonation or booking/ticket/trip/refund powers. Dashboard contains governance/supply counts, never financial values. Future M22 uses a platform-level gateway after M26 and public HTTPS deployment. M27 owns future commission/receivable/settlement; neither milestone is implemented here.
