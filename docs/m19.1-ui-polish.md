# M19.1 — Final UI/UX polish

## Initial audit

Reviewed the M19 standalone gallery (18 real screens), operator/admin/customer components, shared status badges and Vietnam date/money helpers, and installed dependencies before editing. The existing green/orange identity and navigation remain appropriate.

- Dashboard gives financial totals more prominence than operational work.
- Trip rows repeat departure time and leave available capacity information implicit.
- Crew directory uses large cards and the assignment form is permanently expanded.
- Passenger payment, attendance, contacts and actions compete for attention.
- Fleet repeats physical availability and operational readiness as equally prominent badges.
- Maintenance history is as heavy as upcoming work; dates sometimes show raw ISO values.
- Reports expose payment enums and technical cohort terminology.
- Customer detail presents booking, travel and money metrics at the same level.
- Ticket success leaves unused desktop space; admin directory needs only modest refinement.

## Implementation principles

One strongest identity per row, compact textual state, supporting journey/resource information, then muted metadata. Reuse Lucide only for navigation; no new dependencies, decorative icons, animations, business aggregates or per-row requests. Preserve existing payment, cancellation, access-control and reporting semantics.

The implementation and verification results follow.

## Changes delivered

- **Dashboard:** actionable operational counts and links first, then today's trips, fleet warnings and a quieter business summary. One shared report query/poll feeds both presentations. Links lead to supported date-filtered trip lists or booking lookup; they do not pretend to filter unsupported crew/payment states.
- **Trips/workspace:** departure and route lead; date, bus/type/capacity and lifecycle remain scannable. Quick filters use existing server statuses. Workspace exposes crew readiness once, makes lifecycle the primary action and keeps booking secondary. No per-trip crew/passenger requests were added to the list.
- **Crew:** compact responsive personnel rows, one row per employee with multiple capability badges, local capability/active/30-day licence filters, Vietnamese licence dates. Assigned names remain visible while assignment uses a keyboard-accessible native details section. No invented next-trip or individual readiness fields.
- **Passengers:** seat/name first, separate payment and attendance badges next, route supporting, phone/code/time muted. Unpaid collection is primary and unavailable check-in is secondary; eligibility, no-show and multi-seat semantics are unchanged.
- **Assisted booking:** existing M19 steps, seat summary, separated contact/payment fields and mock/reservation wording retained. No flow redesign or extra fetches.
- **Fleet:** plate anchors each row; one operational readiness badge replaces duplicate available/ready badges, with distinct physical exceptions retained. Next trip, maintenance, warnings and an explicit view action remain visible.
- **Maintenance:** server-backed status segments distinguish scheduled, active, completed and cancelled records without inventing a combined history query. Terminal details collapse, while dates/bus/type/state remain visible. Start/complete are primary; cancellation is secondary and still confirmed.
- **Reports:** shared Vietnamese payment labels replace raw payment enums in tables, filters and breakdowns. Cohort terminology replaced with explicit period wording. Counts, null/incomplete load semantics, refund bases and charts retained; filters slightly compacted.
- **Customers:** name links and quieter contact metadata; existing exact booking/travel/payment totals grouped without new aggregates or identity merging.
- **Sidebar:** role-filtered links grouped as Điều hành, Kinh doanh, Nguồn lực and Cấu hình. Existing Lucide reused with functional navigation icons; no new dependency or decorative icon cards.
- **Admin:** operator names lead, contacts/codes are quieter, counts compact and detail actions remain clear. Filter surface improved without new modules/data.
- **Customer ticket:** balanced two-column journey/ticket layout at desktop, one column on mobile, actions near content; success and invalid-ticket behavior retained. Other customer flows unchanged.
- **Dates:** shared Asia/Ho_Chi_Minh formatter renders dd/MM/yyyy and dd/MM/yyyy HH:mm; read-only licence, maintenance, chart and report dates use it. Native inputs retain browser locale and Vietnamese business-date labels/hints. No date-picker dependency.

## Scope and preserved baseline

Continued the current dirty feature/management-upgrade working tree. M19 backend fleet batching, session protection, shared errors, cancellation keyboard behavior and lazy routes were preserved. No backend source, domain, schema, migration or API change was made in M19.1. The existing isolated MySQL data directory and gallery schema were reused without destructive seeding; backend startup reused all 21 seed trips. A single future trip was added through the normal API to demonstrate today's operational warning; browser bookings use fictional demo contacts and mock payments.

## Remaining limitations / V2.0

Trip-list crew/readiness/passenger aggregates and employee next-trip data are not supplied by current list APIs; they were not fabricated or fetched per row. Dashboard operational links are entry points to existing lists. Maintenance history has separate completed/cancelled segments. Wide report/customer tables use contained horizontal scrolling; the document itself must not overflow. Native date-input appearance follows OS/browser locale. Mock payment labels remain explicit.

Deferred to V2.0: richer animations, page transitions, motion systems, sophisticated skeleton transitions, deeper visual/interaction redesign and dashboard customization. M19.1 adds no animation system and preserves reduced-motion behavior.
