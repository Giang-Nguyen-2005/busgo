# BusGo V1.5 release notes

V1.5 business scope is feature-complete through M18C; M19 hardens presentation,
session boundaries, fleet reads and release readiness. Local verification evidence
and unresolved deployment limits are in [M19 verification](m19-verification.md).
This is a demo-capable release candidate, not a real-money payment service.

- Customers: registration/login/profile, Vietnam-date search, segment seat
  availability, temporary holds, server-priced booking, mock payment, electronic
  tickets, owned history and eligible whole-booking cancellation.
- Operator admins: routes/fares, buses/types, trips/workspaces, PHONE reservations,
  PAY_ON_BOARD/QR-link mock collection, crew, attendance/no-show/pickup closure,
  cancellation/refund history, truthful reports, booking-scoped customer directory,
  fleet readiness, planned maintenance and retained status history.
- Operator staff: existing owned operational reads; no new mutation privileges.
  Reports, customer directory and fleet management remain admin-only.
- System admins: operator onboarding/contact/status management and staff visibility;
  no operator operational bypass or platform BI.
- M19: separate reservation/payment labels, compact assisted-booking progress and
  explicit success, centralized status tones, safe shared errors, stale-session
  response rejection, route loading feedback, cancellation keyboard handling,
  lazy home/auth routes and batched fleet planning reads.

Authorization uses JWT plus current account/role/membership checks, owned-object
queries and protected service methods. Anonymous payment links expose only the
minimum journey/payment context and can be replaced/revoked. This is a bounded
source/regression review, not a penetration test or WCAG certification.

All collection/refund amounts are simulated. No bank transfer or real refund is
performed. Electronic QR tickets are demo operational identifiers. Sharing payment
links is manual; there is no Zalo integration or automatic ticket messaging.

Known limits: immutable trip assignments, planned rather than actual travel windows,
date-based maintenance warnings without synchronized mileage, lifetime query-time
customer/report aggregates, all-page selector fetches and nonterminal fleet history
that still grow with data. Demo seed never resets an edited account or trip.
Production TLS/reverse proxy, backups, monitoring, MySQL 8 rollout and scale testing
remain deployment responsibilities. See [deployment](deployment.md).

Deferred after V1.5: real gateways/settlement/accounting, partial cancellation,
seat/trip changes and rescheduling, loyalty/promotions, marketing CRM, chat/reviews,
notifications, GPS/IoT, mileage/parts/procurement, AI, exports, pricing/multi-currency,
new platform modules and expanded staff mutation capabilities.

The [desktop UI gallery](v1.5-ui-gallery.html) presents 19 real demo screens in one
self-contained HTML file; no running server is needed to view it.

## M19.1 final UI polish

Operator screens now prioritize operational work, departure/route, personnel and passenger identity. Compact crew assignment, supported quick filters, one fleet readiness state, quieter maintenance history and grouped customer metrics improve scanning. Reports and operational history use Vietnamese labels; rendered dates consistently use Vietnam time with day/month/year before time. Admin receives modest directory polish; customer success/tickets use a balanced desktop layout.

No backend/domain/API changes or new dependencies. Final frontend verification: 121 tests and production build passed; live UI reviewed at 390, 820 and 1440 in a non-Vietnam browser timezone. The refreshed 18-screen standalone gallery was verified offline after all services stopped. See [M19.1 evidence and limitations](m19.1-ui-polish.md).
